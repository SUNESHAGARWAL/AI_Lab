# evals/datasets

Retrieval-quality golden sets and review data for this project's eval harness
(`packages/evals`). Two files live here with very different trust levels — read this
before touching either.

## `retrieval_golden.jsonl` — the golden set

The source of truth for retrieval quality, per `CLAUDE.md`. One JSON object per
line:

| field | type | meaning |
|---|---|---|
| `schema_version` | int | schema version, currently `1` |
| `id` | string | stable item id |
| `question` | string | the question text |
| `relevant_chunk_ids` | list[string] | ground-truth relevant `chunk_id`s (empty only for `out_of_scope` items) |
| `difficulty` | `easy` \| `medium` \| `hard` | informal difficulty tag |
| `question_type` | `factual_lookup` \| `role_scoped` \| `cross_reference` \| `out_of_scope` | see taxonomy below |
| `provenance` | object | `{author, date, source_reference}` |

**No assistant-authored ground truth ever enters this file directly.** Every item's
`relevant_chunk_ids` mapping must come from a human who read the actual chunk
content and confirmed relevance — see the promotion workflow below. This file ships
empty; it grows only through manual, human-reviewed additions.

### `question_type` taxonomy

This is a **distinct taxonomy from `api.graph.schemas.QueryIntent`** (which has
`factual_lookup` / `role_scoped_applicability` / `out_of_scope`, no
`cross_reference`) — `QueryIntent` classifies live queries for graph routing;
`question_type` here classifies golden-set items for eval breakdown. Do not conflate
or reuse one for the other.

- **`factual_lookup`** — a direct question answerable from a single article/recital
  chunk (e.g. "What does Article 6 say about high-risk classification?").
- **`role_scoped`** — a question naming an explicit role + obligation (AI Act
  provider/deployer; GDPR controller/processor), e.g. "As a deployer of a high-risk
  AI system, what are my obligations under Article 26?".
- **`cross_reference`** — a question whose full answer genuinely spans more than one
  chunk, grounded in the real `metadata->>'cross_references'` values populated
  during ingestion (`apps/ingest/src/ingest/references.py`).
- **`out_of_scope`** — a question clearly outside the AI Act/GDPR corpus, testing
  correct low-relevance/abstention behavior. By definition `relevant_chunk_ids` is
  empty for these — there is nothing a retriever could correctly return.

### Provenance rule

Per `CLAUDE.md`: never add an item without a provenance entry (source, author of the
expected answer, date, difficulty). `author` should be a real person's name (or
handle), not "claude" or an assistant identity — this file only ever records
human-validated ground truth.

## `candidates_for_review.jsonl` — NOT the golden set

> **This file is unverified.** Nothing in `candidate_pool` has been confirmed
> relevant by a human. `relevant_chunk_ids` is intentionally left empty and
> `verified` is `false` on every item. **Never consume this file from
> `run-retrieval` or any automated scoring path** — it exists purely as a review
> aid.

Generated by `evals.cli generate-candidates`: for each of ~40 hand-authored seed
questions (`packages/evals/src/evals/candidate_questions.py`, spanning the
difficulty × question_type taxonomy above and grounded in the real ingested
corpus), the command runs the question through the real `PgVectorRetriever`
against live Postgres and records the real top-k results — `chunk_id`, `score`, and
full `content` — as `candidate_pool`. The harness does not guess or propose which of
those results are "the" relevant ones; that would just be assistant-fabricated
ground truth under a different name. It surfaces the real evidence so a human can
read it and decide.

| field | type | meaning |
|---|---|---|
| `schema_version` | int | schema version, currently `1` |
| `id` | string | seed question id, e.g. `cand-001` |
| `question` | string | the question text |
| `difficulty` / `question_type` | — | same taxonomy as the golden set |
| `candidate_pool` | list[object] | real top-k `{chunk_id, score, content}` |
| `relevant_chunk_ids` | list[string] | **empty until a human fills it in** |
| `verified` | bool | **false until a human flips it to true** |
| `notes` | string \| null | optional reviewer rationale |
| `generated_at` | string | ISO 8601 timestamp of the retrieval run |

### Promotion workflow (manual, human-only — never automated)

1. Run `uv run --package evals python -m evals.cli generate-candidates`.
2. Open `candidates_for_review.jsonl`, read each item's `candidate_pool` content.
3. For items you confirm, fill in `relevant_chunk_ids` with the actually-relevant
   `chunk_id`s, optionally add `notes`, and set `verified: true`.
4. For each reviewed item, manually construct the corresponding `GoldenItem` (with a
   real `provenance` block — your name, today's date, a `source_reference`) and
   append it as a new line in `retrieval_golden.jsonl`.
5. Re-running `generate-candidates` refuses to overwrite `candidates_for_review.jsonl`
   once it contains any reviewed item (`verified: true`, or non-empty
   `relevant_chunk_ids`/`notes`) — pass `--force` if you intend to discard it and
   start over.
